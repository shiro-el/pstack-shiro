### Autopilot-stack

Run the Autopilot-full playbook, but never merge into trunk.

1. **In place of step 5, land on the shared base and stop at verified.** Merges into the program's shared base branch are yours, per step 2. Trunk merges are the operator's. Stop when every PR is in the base and verified, and the base's PR to trunk is green and verified, then hand that PR to the operator. After the handoff, nobody pushes to the base without the operator's go. Every waiter's wake prompt names this file, so each wake sees the no-trunk-merge rule.
2. **Cut one shared base branch and merge into it freely.** At program start, cut `<program>-base` from trunk and push it. Every PR branches from the base's tip and opens against the base, never against trunk or another PR's branch, so no PR sits on another PR and the queue never runs as one line. In place of Autopilot-full step 2's rebase onto trunk, each PR rebases onto the base's tip. Once an owner reports code-ready with its gates green on the base's tip, merge the PR into the base at once, without the operator, and verify it at that head. Never hold a PR out of the base for its verdict or for the operator, because that merge is what frees its dependents. A finding becomes a fix PR into the base with its own verdict. At the end, open one PR from the base to trunk and run a single verifier on it per Autopilot-full step 4.
3. **Classify every dependency before you spawn.** A queue's "blocked by" links mix three kinds of dependency, and only one of them makes a PR wait. Log each edge's class as a decision row.
   - `code`: the child calls, reads, or extends code the parent adds. The child branches from the base once the parent is in it, or earlier per step 4.
   - `file`: both PRs change the same files, a generated file, or an ordered sequence such as migrations, but neither needs the other's code. Run both off the base in parallel. Whichever merges into the base second rebases onto the base's tip first, regenerates generated files instead of hand-merging them, and moves its ordered entries after the ones already in the base.
   - `order`: the order is only how the plan reads. Run both off the base in parallel.

   A serial chain of `file` and `order` edges is the plan's shape, not the work's, so most of the queue can start at once.
4. **Start a child early only on a frozen interface.** A child may start on its parent's code-ready head before the parent is in the base, when its brief names the parent interface it uses, such as a function signature, a schema, or an API contract. If a parent fix round changes that interface, hold the child until the parent is in the base. If it does not, the child only rebases. Once the parent is in the base, the child moves with `git rebase --onto origin/<base> <parent head it started on>`, computed from its own merge-base, never from a head named in a message, because the root can name the wrong one.
5. **Budget the machine before you spawn.** Each owner and each verifier lane that runs the app holds an isolated local environment, such as a worktree with its own databases, ports, and container networks, so one PR under verification can hold three. Before each spawn, count what the machine has free, such as the repo's slot allocator, container networks, and memory, and keep the agents in flight within it. When capacity runs short, the PR the most dependents wait on goes first. Every agent stops its environment when its turn ends, keeping its data, and touches no container, network, volume, or process it did not create, even an idle one, without the operator's go.
